# Дашборд команды продаж «Встречи → Оплата»

Отвечает на один вопрос: **как первичные встречи превращаются в продажи** —
и сколько продаж будет дальше. Данные захардкожены в `src/data/`, обновление
описано отдельным скиллом `update-dashboard-data`.

## Стек и жёсткие ограничения

- **React 18 + Vite 5**, JSX без TypeScript.
- **Графики рисуются вручную в SVG.** Никаких chart-библиотек: recharts, d3,
  chart.js. Всё это осознанное решение — графиков немного, они специфические
  (полоса диапазона, вторая ось, затенение недозревших месяцев), и библиотека
  дала бы больше борьбы с ней, чем пользы.
- **Стили — инлайн-объекты + CSS-переменные.** Ни Tailwind, ни CSS-in-JS.
  Общие стили лежат в `src/utils/styles.js` как обычные объекты.
- Никакого стейт-менеджера: всё состояние — `useState` в `App.jsx` и вкладках.

```bash
npm create vite@latest . -- --template react
npm i   # react, react-dom, vite, @vitejs/plugin-react — больше ничего
```

## Дизайн-система

Тёмная тема по умолчанию, светлая по переключателю. Токены на `:root`,
светлая — через `:root.light`, поэтому переключение это один класс на `<html>`.

```css
:root {
  --background: #0C0D10;  --card: #16181D;
  --accent: #39AA5D;      --destructive: #FA4C49;
  --chart-1: #39AA5D; --chart-2: #5383F4; --chart-3: #FCA92F;
  --chart-4: #FA4C49; --chart-5: #D76BFE; --chart-6: #14B8A6;
  color-scheme: dark;
}
:root.light { --background: #F7F8FA; --card: #FFFFFF; color-scheme: light; }
```

- Шрифт **Nunito Sans**, self-hosted в `public/fonts` (woff2, latin+cyrillic,
  400/500/600/700). Не Google Fonts по CDN.
- Тема применяется **до первой отрисовки** — инлайн-скрипт в `<head>`, иначе
  светлая тема мигает тёмным фоном:
  ```html
  <script>try{if(localStorage.getItem("theme")==="light")
    document.documentElement.classList.add("light")}catch(e){}</script>
  ```
- Цвета команд: `MS1 #5383F4`, `MS2 #FCA92F`, `MS3 #39AA5D`.
- Ширина контента 1120px. Не 960: на 960 не помещается строка подвкладок.
- Плоский стиль: без теней и градиентов, границы `1px`, радиусы 8–10px.

## Навигация

Верхний уровень: **Аналитика · Прогноз**. У прогноза подвкладок нет, поэтому
строка второго уровня для него не рисуется вовсе.

Подвкладки аналитики:

1. **Общая динамика** — KPI, график конверсии, таблица команд с раскрытием.
   Контролы в одной строке под табами: `Конверсия` (в продажу / во 2-ю
   встречу) · `Встречи` (все / горячие / холодные) · `Разрез` (месяцы /
   кварталы). Разрез общий для графика и таблицы — иначе они рассинхронятся.
2. **Рейтинг консультантов** — четыре колонки, в каждой топ-3, антитоп-3 и
   полная таблица: закрытых сделок, конверсия в продажу, конверсия в
   повторную встречу, качество встречи.
3. **Качество первой встречи** — 5 критериев, фильтры по уровню и сегменту,
   попап со списком сделок и ссылками в Pipedrive.

## Методология прогноза — самая важная часть

Прогноз отвечает на вопрос **«сколько сделок закроется в этом месяце»**, а не
«сколько продаж принесут встречи этого месяца». Это разные величины, и путать
их — главная ошибка, которую здесь легко совершить.

```
продажи(T) = Σ      Σ      встречи(M, канал) × конверсия(канал) × лаг(канал, T−M)
          M=T…T−8  канал
```

Четыре компонента:

**1. Поток встреч.** До последнего месяца с данными — факт. Дальше: встречи
того же месяца год назад × рост за последние 3 месяца год к году, отдельно по
горячим и холодным.

**2. Конверсия по каналу** с поправкой на зрелость. Наблюдаемые продажи делятся
на долю сделок, успевших закрыться к дате выгрузки:

```js
conv = Σ(наблюдаемые продажи / зрелость(месяц)) / Σ встречи
```

Без поправки конверсия систематически занижена, потому что даже «дозревшая»
база на 6–8% не добрана. Диапазон — интервал Вильсона (z = 1.96).

**3. Цикл сделки** — распределение лага «первая встреча → закрытие», **своё у
каждого канала**, каждый ряд в сумме даёт 1.0:

```js
export const WIN_LAG = {
  hot:  [0.143, 0.327, 0.122, 0.184, 0.102, 0.020, 0.082, 0.020, 0.000],
  cold: [0.146, 0.292, 0.125, 0.146, 0.083, 0.083, 0.104, 0.000, 0.021],
};
```

**Лаг 0 входит в свёртку** — 14% сделок закрываются в месяц самой встречи.
Формулировка «месяц наполняется только сделками прошлых месяцев» неверна.

**4. Две разные оси времени.** Держать в голове постоянно:

| | привязка | где используется |
|---|---|---|
| `consultants.js` → `sales` | месяц **первичной встречи** | конверсия, эффективность |
| `salesFact.js` → `won` | месяц **закрытия** (`Won time`) | факт месяца, рейтинг закрытий |

Годовые итоги по ним не сходятся и не должны: в 2026 закрываются сделки со
встреч 2025, а встречи конца 2026 закроются в 2027. **Делить одно на другое
нельзя** — «CR» из этих двух чисел бессмыслен.

Полезное для UI: доля прогноза месяца, обеспеченная **уже прошедшими**
встречами. Считается по объёму (`fromKnown / mid`), а не по сумме весов —
у каналов разные ядра и разный вклад. У ближайшего месяца ~85%, у декабря ~25%.

## Приёмы, которые стоит повторить

**Недозревшие месяцы затеняются.** Последние ~3 месяца по конверсии в продажу
занижены. На графике это серая зона с подписью, в тренде такие месяцы
исключены, в таблице помечены.

**Полноколоночные мишени для тултипа.** Наведение на 8-пиксельную точку не
работает. Прозрачный `rect` на всю высоту колонки, самым верхним слоем:

```jsx
<rect className="chart-hit" x={left} y={padT} width={right-left} height={innerH}>
  <title>{lines.join("\n")}</title>
</rect>
```

**Порог наблюдений в рейтингах.** Горячих встреч на человека медианно 7, и
конверсия по ним — шум. Селектор минимума (3/5/10/20), ниже порога ячейки без
заливки, люди — в блок «вне рейтинга». Тай-брейк: у долей выше тот, у кого
больше наблюдений; у абсолютных величин наоборот, и **зависит от направления**
рейтинга (в топе меньше встреч лучше, в антитопе больше встреч хуже).

**Нормировка цвета под масштаб метрики.** Единая шкала «красный → зелёный»
врала бы: 15% в продажу это отлично, 15% качества — провал. Для абсолютных
величин нормировка на лучший результат периода, а не на константу.

**Пресеты периода.** Период по умолчанию — пересечение источников, и годовой
итог в нём не виден. Кнопки «Весь год / Всё время / Пересечение источников».

**Команда привязана к месяцу.** Переход консультанта не должен переписывать
историю. `team` — текущая, `teamHistory: [{ until, team }]` — прошлые отрезки,
агрегация режется по месяцам. Перешедший виден в обеих командах со своим
отрезком, сумма по командам остаётся равна итогу.

## Проверка перед сдачей

```bash
npm run build
```

Дальше — headless-браузер: `npx playwright-core` с
`/opt/pw-browsers/chromium-*/chrome-linux/chrome`. Проверять:

1. Все вкладки открываются, `pageerror` и `console.error` пусты.
2. Обе темы: тёмная и `:root.light`.
3. Таблицы не переполняют колонку — замерить `scrollWidth − clientWidth`.
4. Тултипы: `rect.chart-hit title` содержит ожидаемые строки.
5. Инварианты данных: горячие ≤ всего, продажи ≤ встречи, повторные ≤
   первичные, **сумма по трём командам равна общему итогу**.

Скриншоты смотреть глазами: наложения подписей на графиках и обрезанные
столбцы в таблицах не ловятся ничем, кроме взгляда.

## Чего в дашборде нет

- Денег: считаются штуки сделок, не суммы.
- Встреч людей вне отчётов по консультантам — новых сотрудников надо
  добавлять в ростер явно.
- Неопределённости потока встреч и самого цикла сделки в диапазоне прогноза:
  там только интервал конверсии, поэтому реальный разброс шире.
