# Обновление данных дашборда «Встречи → Оплата»

Все данные захардкожены в `src/data/`. Чтобы их обновить, нужно прислать
выгрузки из Pipedrive: графические отчёты — PDF, табличные (списки сделок,
оценки встреч) — **XLSX**.

## Что прислать — чек-лист

Каждая строка ниже — отдельная выгрузка из Pipedrive. Можно слать в любом
порядке; парные графики (встречи + продажи/повторные) удобнее слать вместе.

| # | Выгрузка (отчёт Pipedrive) | Что внутри | Период | Куда идёт |
|---|---|---|---|---|
| 1 | **Встреча → оплата по консультантам** | 2 графика на консультанта: «Встречи …» (дискавери) + «Продаж из встреч …» (фильтр **WON**) | окт'24 – тек. месяц | `consultants.js` → `meetings`, `sales` |
| 2 | **Горячие встречи** | «Горячие встречи …» + «Горячих продаж …» (фильтр **WON** + заявка/ивент/контент) | окт'24 – тек. месяц | `consultants.js` → `hotM`, `hotS` |
| 3 | **Встреча → повторные** | «Встречи …» + «Повторные из встреч …» (этап «вторая встреча, презентация оффера для ЛПР») | с 16.02.2026 | `secondMeetings.js` |
| 4 | **XLSX оценок первичных встреч** | колонки: консультант, дата, 5 критериев (баллы) + итог, ссылка на сделку, уровень и сегмент | по датам в файле | `meetingQuality.js` |
| 5 | **Факт продаж по консультантам** (`deals*.xlsx`) | список сделок: **Won time**, **Owner**, Deal created, Title, Deal value | янв **прошлого** года – сегодня | `salesFact.js` → факт по месяцу закрытия |

Дополнительно: для новых консультантов, которых нет в основном отчёте
(например, недавно вышедших), обычно приходит отдельный 1-страничный PDF —
его данные добавляются к тому же консультанту.

**Агрегат «Встречи для прогноза» (общее количество встреч по SG) больше не
нужен.** Раньше он шёл в `meetings.js`, но прогноз перешёл на встречи по
консультантам, и как сверка агрегат не работает: он включает всех, кто когда-либо
был в команде, поэтому в 2025 расходится с суммой по консультантам на 30–85
встреч в месяц из-за уволившихся, а не из-за ошибок извлечения. Сверять надо
отчёты #1 и #3 между собой (см. «Проверки качества»). `meetings.js` остался в
репозитории как замороженная история и никем не импортируется.

### Отчёт #5 — требования к выгрузке

Это **список сделок** (Deals → Export), а не график, поэтому у него свои
правила.

**Формат — XLSX.** Не PDF: Pipedrive печатает таблицу «как на экране», правые
колонки уходят за край листа, а строки ниже видимой области обрезаются —
именно нужные `Won time` и `Owner` теряются первыми. XLSX отдаёт все строки
и все колонки. Имя файла обычно вида `deals<id>.xlsx`.

**Колонки.** В экспорт попадает весь набор полей вьюхи; лишние не мешают,
парсер берёт по имени заголовка. Обязательны две:

| Колонка в файле | Зачем |
|---|---|
| `Deal - Won time` | месяц продажи (дата-время закрытия) |
| `Deal - Owner` | продавший консультант |
| `Deal - Deal created` | дата создания сделки — прокси даты первичной встречи |

`Deal created` не обязателен, но полезен: по паре «создана → закрыта» можно
сверить цикл сделки, который приходит от команды продаж отдельно (см. ниже).
Желательны, но не критичны: `Deal - Title`, `Deal - Value` (сумма).

**Фильтр:** стадия **WON**, пайплайн **SG-сегмент**, период — **с января
прошлого года** (не текущего): нужен полный предыдущий год, иначе не с чем
сравнивать месяцы год к году.

**Что делать с данными:** сгруппировать по `Won time` (месяц) и по `Owner`.
Это другая нарезка, чем в отчётах #1–2, где продажи привязаны к месяцу
**первичной встречи**. Обе нужны: атрибуция к встрече показывает конверсию,
атрибуция к закрытию — факт месяца и скорость дозревания сделок.

**Мапинг `Owner` на консультантов.** В выгрузке имена латиницей, в
`consultants.js` они лежат в поле `fullName` — сопоставлять надо по нему, а не
по русскому `name`. Две ловушки:

- написание расходится (в выгрузке встретилось `Максим Sadykov` вместо
  `Maxim Sadykov`) — держать словарь исключений `ALIAS`;
- часть владельцев вообще не из текущего состава SG: уволившиеся продавцы,
  `(deleted user)`, смежные роли. Их не выбрасывать — складывать в
  `SALES_FACT_OTHER`, чтобы сумма по месяцам сходилась с выгрузкой,
  и показать пользователю список.

**Итоги не сойдутся с отчётами #1–2, и это нормально.** В «продажах за 2026»
по месяцу закрытия сидят сделки со встреч 2025 года, а сделки со встреч
конца 2026 закроются уже в 2027. Расхождение — не ошибка выгрузки, сверять
эти два числа между собой не нужно.

## Важные детали выгрузок

- **Продажи = только стадия WON** (в фильтре отчёта должно быть `WON`).
- **Горячие** = фильтр `ЗАЯВКА (=ГОРЯЧАЯ), ИВЕНТ НОВЫЙ, КОНТЕНТ НОВЫЙ`.
  Холодные = все − горячие (отдельно слать не нужно, считается само).
- **Продажи привязаны к месяцу первичной встречи**, а не закрытия сделки —
  во всех графических отчётах (#1, #2, #3). Исключение — отчёт #5, там
  наоборот, месяц закрытия (`Won time`).
- **Последние 3 месяца не дозрели.** Сделка закрывается в среднем через
  ~2.5 месяца после первичной встречи, поэтому продажи трёх последних месяцев
  в отчётах #1/#2/#3 всегда занижены — это не ошибка выгрузки. На вкладке
  «Общая динамика» такие месяцы затенены; в прогнозе занижение компенсируется
  поправкой на зрелость когорт.
- Отчёт #3 (повторные) — период только с момента появления этапа
  «вторая встреча» (16.02.2026), а не весь диапазон.
- Команда консультанта (MS1/MS2/MS3) берётся из префикса в заголовке графика.
- **Переходы между командами.** В выгрузке человек приезжает уже с новой
  командой за все месяцы, поэтому по PDF переход не видно — про него надо
  спрашивать отдельно. Статистика по командам режется по месяцам: встречи мая
  уходят той команде, в которой человек был в мае. Хранится это так:

  ```js
  // Перешёл из MS2 в MS1 с авг'26
  { name: "Максим", team: "MS1",
    teamHistory: [{ until: "2026-07", team: "MS2" }], … }
  ```

  `team` — текущая команда (чипы, рейтинги, состав), `teamHistory` — прошлые
  отрезки, отсортированные по `until` (включительно). Помощник `teamOf(d, month)`
  в `src/utils/teams.js`. Поле надо продублировать во всех файлах, где есть
  человек: `consultants.js`, `secondMeetings.js`, `salesFact.js`. В
  `meetingQuality.js` дублировать не нужно — там команда лежит в каждой записи
  (`t`) и уже привязана к дате встречи.

  После правки сверить: сумма встреч и продаж по трём командам должна равняться
  общему итогу. Перешедший человек показывается в обеих командах, каждая со
  своим отрезком месяцев, и помечен чипом «→ MS1» в раскрытой команде.

## Как Claude извлекает данные (для исполнителя)

1. **XLSX читать через openpyxl**, а не конвертировать в что-то ещё:
   ```python
   import openpyxl
   ws = openpyxl.load_workbook(path, data_only=True).active
   rows = list(ws.iter_rows(values_only=True))
   hdr = rows[0]                      # брать колонки по имени заголовка,
   i = hdr.index('Deal - Won time')   # а не по позиции — состав полей плавает
   ```
   `data_only=True` обязателен, иначе вместо значений придут формулы.
2. **PDF — сначала текстом, не картинкой.** `pdftotext -bbox-layout file.pdf -`
   отдаёт слова с координатами — этого хватает и для таблиц, и для графиков
   (числа над столбцами кластеризуются по x). Рендер в PNG нужен только
   когда текстового слоя нет. Пачка страниц-картинок упирается в лимит
   размера запроса (32 МБ), текст — нет.
3. Если картинка всё же нужна: `pdftoppm -r 300 -png …`. Если poppler не
   установлен — `apt-get install -y poppler-utils`.
4. Резать каждую страницу на **полноширинные полосы** (W ≈ 2483 px при 300 DPI),
   отдельно заголовки графиков и области со столбцами — иначе обрезаются
   правые месяцы или числа.
5. **Порядок консультантов в разных отчётах может отличаться** — всегда
   считывать заголовок каждого графика, не полагаться на позицию.
6. **Проверки качества перед записью:**
   - горячие ≤ всего (по каждому месяцу и встреч, и продаж);
   - **первичные встречи из отчёта #1 равны первичным из отчёта #3** — по
     каждому человеку и месяцу, не только в итоге. Это главная перекрёстная
     проверка: два независимых PDF на одной и той же выборке. Исключение —
     месяц появления этапа «вторая встреча» (фев'26): отчёт #3 считает его
     с 16-го числа и законно даёт меньше. Расхождение в других месяцах —
     повод перечитать графики, а не выбирать цифру на своё усмотрение:
     показать пользователю обе;
   - продажи ≤ встречи;
   - в отчёте #5 есть обе обязательные колонки (`Won time`, `Owner`), ни в
     одной строке `Won time` не пустой, а сумма
     `SALES_FACT + SALES_FACT_OTHER` по месяцам равна числу строк в файле.
   Несостыковка обычно значит перепутанные графики (встречи/продажи) —
   перечитать заголовки.
7. **Неполные выгрузки не достраивать по догадке.** Если не хватает колонки
   или строк — сказать об этом и попросить переэкспорт, а не восстанавливать
   значения из соседних отчётов.
8. После обновления: `npm run build`, затем закоммитить и запушить в рабочую
   ветку. Перед записью присылать пользователю извлечённые числа на сверку.

## Структура файлов данных

- `src/data/consultants.js` — массив `D`: `{ name, fullName, team, teamHistory?, meetings, sales, hotM, hotS }`, ключи месяцев `"YYYY-MM"`.
- `src/utils/teams.js` — `teamOf(d, month)`, `wasInTeam(d, team, months)`: команда с учётом переходов.
- `src/data/secondMeetings.js` — `SECOND_MEETINGS`: `{ name, team, m1, m2 }` + `SM_MONTHS`.
- `src/data/meetingQuality.js` — `MEETING_QUALITY`: `{ c, t, d, s:[5] }` + `MQ_CRITERIA`, `MQ_MAX`.
- `src/data/meetings.js` — `HIST_HOT`, `HIST_COLD` (агрегат SG по окт'24–июл'26).
  Заморожен, ничем не импортируется, обновлять не нужно.
- `src/data/salesFact.js` — `SF_MONTHS` + `SALES_FACT`:
  `{ name, fullName, team, won }`, где `won` — продажи по месяцу **закрытия**
  сделки (`Won time`). Плюс `SALES_FACT_OTHER` (владельцы вне состава SG),
  `WON_BY_MONTH` (итог по месяцам), `CLOSE_OBS_MONTH` (месяц выгрузки) и
  `WIN_LAG` / `WIN_LAG_META` — распределение цикла сделки, см. ниже.

### Цикл сделки (`WIN_LAG`) — приходит от команды продаж

Прогноз — свёртка потока встреч с распределением лага «первая встреча →
закрытие», **отдельным для горячих и холодных**. Это распределение не
выводится из выгрузки, его задаёт команда продаж; спросить актуальную версию,
если данные обновляются спустя долгое время.

Формат — два ряда долей по месяцам 0…8, каждый в сумме 1.0:

```js
export const WIN_LAG = {
  hot:  [0.143, 0.327, 0.122, 0.184, 0.102, 0.020, 0.082, 0.020, 0.000],
  cold: [0.146, 0.292, 0.125, 0.146, 0.083, 0.083, 0.104, 0.000, 0.021],
};
```

`WIN_LAG[канал][k]` — доля **всех** продаж канала, закрывающаяся через k
месяцев после встречи. Конверсия в них уже учтена: 100% = все потенциальные
продажи канала. При обновлении пересчитать `WIN_LAG_META` (`meanMonths`,
`medianMonths`, `closedBy6`) и проверить, что каждый ряд суммируется в 1.0.

Проверка адекватности: свёртка `встречи × конверсия × WIN_LAG` должна давать
по прошлому году примерно фактическое число закрытий **у консультантов из
отчётов по встречам** (не по всей выгрузке — там есть владельцы вне состава).
Расхождение больше 20% на годовом горизонте значит, что либо конверсия
посчитана по недозревшим когортам, либо распределение лага устарело.

Если меняется горизонт прогноза — обновить `FORECAST_START` в `src/constants.js`
(первый месяц без факта).
